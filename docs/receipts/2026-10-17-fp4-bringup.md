## Control and rollback

The previous serving model was DeepSeek V4.1 Flash
(`dsv41-serve:v4`, unit `vllm-dsv41-two-sparks.service`). It was stopped
through its unit, and its watchdog timer was stopped first:

```bash
systemctl --user stop vllm-dsv41-two-sparks-watchdog.timer
systemctl --user stop vllm-dsv41-two-sparks.service
```

Both units are `inactive` and the DSV tree was not modified. Rollback:

```bash
cd /home/nvidia/glm53-fp4-local && ./launch.sh down
systemctl --user start vllm-dsv41-two-sparks.service
systemctl --user start vllm-dsv41-two-sparks-watchdog.timer
```

| Arm | KV | Tokens | 500k concurrency | Free / available | Result |

| 11 GiB cap | `--kv-cache-memory-bytes 11G` | 1,343,283 | 2.69× | ~10 / ~9.5 GiB | below 2M |
| Model-card command | `0.87`, no cap | 1,944,029 | 3.89× | ~4.8 / ~3.9 GiB | 97% of 2M |
| **Adopted** | **17G + `--mm-processor-cache-gb 0`** | **2,078,358** | **4.16×** | **~4.9 / ~3.7 GiB** | **2M PASS** |

The image's `fp8_ds_mla` layout costs about 8.8 KiB/token, not the naive
5.6 KiB: 11 layers × (512 latent + 256 V) + the kpool indexer. That is why the
11G arm fell short.

Boot timeline for the adopted arm: weights 83.62 GiB loaded in 149.7 s (warm
page cache; 235.8 s on the first boot), B12X routing 2.5 min, KV allocation
and API ready about 5 min after launch. The first boot took about 11 min
because the B12X autotune compiled 2,955 programs; later boots reuse
`~/.cache/b12x`.

`prefix_cache` is a `WARN`, not a failure: the DGX Spark recipe does not set
`--enable-prompt-tokens-details`, so `usage.prompt_tokens_details.cached_tokens`
is not exported. The smoke request pair does not prove a hit or a miss from
that field. Add the flag for per-request cache accounting.

## Memory margin — read before calling this production

After the 2M boot:

```
Mem: 124610 total, 120910 used, 4877 free, 2205 buff/cache, 3699 available
```

~4.9 GiB free and ~3.7 GiB available. The pool is preallocated, but GB10 has
no OOM killer. Do not co-locate builds, downloads, or another model on these
nodes while this arm is resident. If stability is more important than the
last 3.9% of capacity, drop to `16G` (~1.956M) or the model-card `0.87`
command (1.944M).

## Speed matrix (2026-10-17, after bring-up)

Harness: `scripts/speed_matrix.py`. Prompts are unique random token-ID
sequences (no shared prefix, no cache hits). Prefill TTFT is request start to
first streamed token; prefill tok/s is prompt tokens / TTFT. Decode is 200
tokens with `ignore_eos`; decode tok/s is measured between the first and last
token. Acceptance is the `/metrics` delta for the cell. Full tables:
[2026-10-17-speed-matrix.md](2026-10-17-speed-matrix.md) and
[the JSON](2026-10-17-speed-matrix.json).

**Prefill, no cache — per-request median tok/s** (aggregate in parentheses):

| Conc | 8k | 16k | 32k | 64k | 128k |
|---:|---:|---:|---:|---:|---:|
| 1 | 2,108 (2,107) | 2,282 (2,281) | 2,269 (2,268) | 2,237 (2,237) | 2,192 (2,191) |
| 2 | 1,342 (2,295) | 1,481 (2,274) | 1,570 (2,259) | 1,609 (2,235) | 1,610 (2,192) |
| 4 | 789 (2,296) | 859 (2,279) | 894 (2,261) | 908 (2,239) | 904 (2,198) |
| 8* | 466 (2,302) | 487 (2,286) | 496 (2,269) | 499 (2,246) | 492 (2,199) |

\* concurrency 8 exceeds `--max-num-seqs 4`; those requests queue, so their
per-request TTFT includes queue time. The aggregate column is the better
throughput comparison there. Single-request 128k prefill TTFT was 59.8 s;
at c=8 it was 270.0 s for the first wave, 436.4 s p90.

**Decode, 200 tokens — two passes** (tok/s per request / aggregate):

| Conc | Pass 1 tok/s | Pass 2 tok/s | Aggregate 1 / 2 | Mean accept len 1 / 2 | Draft accept rate 1 / 2 |
|---:|---:|---:|---:|---:|---:|
| 1 | 42.90 | 46.76 | 38.92 / 42.43 | 3.431 / 3.685 | 0.486 / 0.537 |
| 2 | 41.73 | 44.54 | 66.07 / 77.08 | 5.103 / 4.914 | 0.821 / 0.783 |
| 4 | 19.63 | 20.25 | 52.39 / 46.39 | 3.038 / 2.671 | 0.408 / 0.334 |
| 8* | 26.60 | 29.77 | 72.30 / 81.80 | 3.651 / 3.873 | 0.530 / 0.575 |

The c=4 decode dip reproduces across both passes (19.6/20.3 tok/s) and is not
explained by this receipt. Do not tune on it without a dedicated window.
Acceptance is also noisy at c=4 (2.7–3.0 mean); the c=2 pass 1 value (5.1) did
not repeat exactly (4.9).

Memory during the matrix stayed at ~2.2–2.4 GiB available and the server stayed
healthy (health 200 throughout). That is thinner than the post-boot 3.7 GiB;
the matrix is the reason the memory-margin warning is not theoretical.
