## Measurement

Freeze the revised harness commit before running it; record SHA256 and command
with both arms. Run the fixed no-cache ladder 8192, 16384, 32768, 65536, 131072,
at concurrency 1, 2, 4, 8; three repetitions. Same seed schedule across arms,
different prompts across no-cache cells and repetitions. Record cap=4 at c8.
Warm the 8k prefill at each concurrency before its first measured ladder.

Decode uses the harness's fixed code, prose and structured-output tasks,
tokenized through the server's actual chat template with explicit
`chat_template_kwargs={"reasoning_effort":"max"}`, temperature=0, seed=0,
ignore_eos, exactly 200 output tokens. These are
first-200-generated-token workloads, often reasoning rather than final
answers. They are not a substitute for representative production traffic
or an evaluation of completed code/JSON.
For each workload/concurrency/repetition, run and discard one complete
200-token batch immediately before the measured batch. Record warmup results
separately; measure acceptance only across the measured batch. Both arms must
have identical tokenized prompt hashes. Warm decode prefixes are intentional;
prefill remains unique and must have zero cache-hit delta.

Use per-request usage and timings, plus per-cell speculative counter deltas.
Retain output text to inspect corruption and semantic behavior. Use incremental
receipts; an interrupted, incomplete, errored or cached-prefill run cannot pass.
No unrelated inference requests may overlap measurement. Check the actual
configured MTP depth in the launch command before measuring the candidate.

## Decision

All functional checks must pass, the image/checkpoint must remain unchanged,
and neither KV bytes nor usable capacity may shrink. Run the existing API,
tool-call, reasoning and prefix-cache smoke in both arms. Any CUDA/Xid error,
rank loss, nonfinite/corrupt output or sustained swapping aborts to baseline.

Compare matched-cell medians and all raw reps. A regression greater than 2%
in prefill/decode rate reproduced in at least two of three reps rejects the
candidate; effects inside the observed control spread are inconclusive.
Require a repeatable gain of at least 2% in a real-text decode workload,
without robust regression in the other workloads or prefill. Otherwise keep
the incumbent. Acceptance is diagnostic for this depth experiment: report both
1+accepted/drafts and accepted/drafted; the former has a different maximum at
K=3 and K=5 and cannot alone decide the comparison. A draft acceptance-rate
regression greater than 2% in two reps rejects. Do not weaken these thresholds
after viewing candidate results.

explains why random input distributions distort speculation and MoE routing.

shared-prefix client retains response text/token evidence and request timings.

only; no EXL3 execution or checkpoint is used.

and the exact deployed fork found native batch-dependent and acceptance-window
controls already available. Their extra graph widths and prefill-counting
behavior justify a separate adaptive-depth window. They are not bundled into
this fixed-depth arm. Reviewed local Exllamav3 `draft_confidence.py` and
TensorFold GLM `cuda_engine.zig` / `cuda_prefix.zig` before freezing the patch.

## Invisible-token timing correction before candidate measurement

The explicit-max baseline stopped at its c4/8k warmup. One request generated
one token with exact usage and `finish_reason=length`, but empty text. The
harness rejected it. Replaying the identical prompt with token IDs proved the
token was 119; enabling special-token rendering still produced empty text.
The server remained healthy. This was a text-timing defect, not evidence of
a failed generation or a kernel fault. The incomplete explicit-max receipt
remains archived and excluded.

The corrected harness requests `continuous_usage_stats=true` and timestamps
increases in cumulative completion usage on SSE choices. It stores those
counts/arrival times, validates monotonic bounded progress, and still requires
matching final usage, exact budget, terminal reason and DONE. It never counts
chunks as tokens or substitutes the final response time for a missing first
token. Live reproduction and the deployed completion-serving source confirm
the per-chunk usage contract; Exa also located vLLM's benchmark comment that
special tokens can have empty text. TensorFold's text-only timing would not
resolve this case, so its helper is not copied blindly.

Both complete arms now use the corrected frozen harness and fresh seed
**2026110303**. Receipts: `local/ab-20261103/token-usage`; baseline unit
`glm53-ab-usage-base-20261103.service`. The short qualification uses another
seed and does not decide adoption. Maximum reasoning effort, prompts/tasks,
budgets, matrix, sampling, controls and decision thresholds remain as above.
MTP3 has still not been activated. These corrections occur during measurement
qualification, before any candidate numbers.

## Streaming interpretation (no gate change)

Review of retained arrivals found that the first cumulative-token update can
contain several tokens, especially for queued requests. The frozen harness's
`(N-1)/(last-first update)` formula follows the reciprocal-TPOT convention;
it does not observe the generation time of each token within a bundle. Its
aggregate field uses `sum(N-1)/cell wall`, so it is normalized rather than
full generated-token throughput. The same frozen harness remains running;
no requests, thresholds or primary comparison metrics change.

The comparator now adds separately labeled diagnostics calculated from the
same retained evidence: `(N-first_update_count)/(last-first update)` and
`sum(N)/cell wall`. They expose bundling sensitivity without guessing token
timestamps or silently replacing the registered gate. They are not a new
adoption criterion. The report renderer also spells out the existing formulas
for future receipts; raw receipts from this window remain unchanged.

Exa review of [vLLM's client metric definitions](https://docs.vllm.ai/en/stable/benchmarking/cli/)
and [multi-turn benchmark](https://github.com/vllm-project/vllm/blob/main/benchmarks/multi_turn/benchmark_serving_multi_turn.py)
preceded this clarification. Local vLLM `calculate_metrics`, Exllamav3's
generator timing boundaries and TensorFold `tools/bench_timing.py` were
checked: engine timings and client SSE timings must not be conflated.
TensorFold's all-generated-token workload rate supports the complementary
whole-cell diagnostic. A bundled-first-update regression verifies that these
diagnostics differ while the frozen primary comparison remains unchanged;
all 16 comparator tests pass.
